# 文件 Agent 插件设计

## 定位

这里的 Agent 是“能观察目录、生成文件操作计划并执行计划的插件”，不要求聊天界面，也不要求接入大模型。规则整理、批量重命名、重复文件检查、自然语言命令或远端模型都可以使用同一能力边界。

Agent 只负责三件事：

1. 查询文件元数据和允许读取的内容。
2. 生成可预览、可确认的结构化操作计划。
3. 把计划交给宿主文件事务服务执行，并按历史节点回退或切换分支。

插件不应直接用 `java.io.File` 修改文件。否则普通 UI、其他插件和 Agent 会形成彼此不可见的历史，树形回退也无法保证真实文件状态与游标一致。

## 推荐边界

文件能力应继续采用 `PluginHost` 的可选 provider 模式，在 `plugin-api.file` 增加独立能力，而不是给 `PluginHost` 增加新的必实现成员。建议拆成：

- `query`：按目录、名称、扩展名、大小、修改时间和递归深度查询，结果受数量和读取范围限制。
- `preview`：把 `move`、`copy`、`rename`、`trash`、`mkdir`、`writeText` 等结构化命令解析成实际源路径、目标路径和冲突报告，但不修改磁盘。
- `commit`：在宿主的单线程文件执行器中原子执行计划，成功后只创建一个历史节点。
- `history`：读取节点和分支；执行 `undo`、`redo(childId)` 或 `checkout(nodeId)`。

插件提交的是声明式命令和前置条件，不是可执行闭包。前置条件至少包含“源仍存在、目标仍不存在”；对覆盖或内容修改可附带大小、修改时间或摘要。预览之后文件发生外部变化时，提交应失败并要求重新预览，不能静默改用新的编号目标。

## 树形历史

每个成功事务创建一个节点：

```text
root
└─ 1 整理截图
   ├─ 2 按月份归档
   └─ 3 按项目归档  ← current
```

在节点 2 撤回到节点 1 后执行新事务，会创建节点 3，节点 2 仍被保留。切换到任意节点时：

1. 找到当前节点与目标节点的最近公共祖先。
2. 逐个执行 `undo` 回到公共祖先。
3. 沿目标分支逐个执行 `redo`。
4. 每一步成功后才移动游标；失败时停在磁盘实际到达的节点。

当前实现已经提供会话内的 `FileHistoryController`，现有创建、删除、复制、移动和重命名会记录双向动作。菜单中的“重做”默认选择当前节点最新的子分支。后续历史页或 Agent 可以通过节点 ID 显式选择旧分支。

## 数据与恢复约束

树形操作历史不是文件快照系统。复制的重做会读取当时的源路径；若源内容已被外部修改，除非事务保存了摘要或内容快照，结果可能与第一次不同。

当前回收数据位于 `.ane-filemanager-trash`，应用重启时会清理，因此历史仍是会话级。若要跨进程恢复，必须同时持久化：

- 历史节点、父子关系、当前游标和命令描述。
- 删除、覆盖及写入前内容的不可变 payload；不能只保存临时路径。
- payload 引用计数和空间上限；只有没有任何分支引用时才能回收。
- 文件身份和前置条件，用于识别外部修改与路径复用。

不建议第一版直接做跨进程历史。先完成会话级事务 API、预览和明确确认，再增加持久化。

## 安全与交互

- 查询和修改必须限制在宿主授予的根目录内，并在解析符号链接后再次检查边界。
- 删除统一进入回收 payload；覆盖必须在计划中显式显示。
- 默认展示“将移动/重命名/删除多少项”和冲突，不让模型直接确认高风险操作。
- 一次 Agent 计划对应一个历史节点；不要让每个文件各占一个节点。
- 查询结果应分页或限制数量，大文本继续使用现有 `host.files` 大小限制。

## 实施顺序

1. 树形双向历史与现有 UI 操作接入（已完成基础实现）。
2. 把文件执行器、事务提交和历史所有权下沉为宿主共享服务。
3. 在 `plugin-api.file` 暴露查询、预览、提交和历史的可选 provider。
4. 实现一个不依赖模型的“整理规则”内置插件，验证能力边界。
5. 再接自然语言解析或模型；模型只生成结构化计划，不直接操作路径。
